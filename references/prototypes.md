# Testing a language through prototypes

Use this branch when the user requests prototypes, implementation, or an explicit test of an existing language. Follow the requested scope, stack, and number of directions.

1. **Choose representative content.** Use a real or realistic page area with the main visitor task, one demanding component, and enough text to expose hierarchy and density. Marketing projects might use an introduction and proof section; applications might use a table, form, or empty state. Label invented content.
2. **Make the comparison informative.** If the user has not specified a count, two or three small directions usually test more than six polished full pages. State which terms each emphasizes and which decision it tests. Change composition or density meaningfully; palette swaps alone reveal little. A wild card is useful only when the user wants exploration.
3. **Build within the constraints.** Use the project's existing stack and assets where possible. Give narrow layouts, keyboard and touch interactions, and reduced motion a functional interpretation. Keep mock data and prototypes isolated from production behavior.
4. **Inspect what you built.** With visual tools, view each relevant layout and state, then repair visible failures. Record what you checked. Without those tools, provide the artifact and clearly mark visual and interaction checks unverified; source review cannot stand in for a rendered review.
5. **Learn from the user's choice.** Ask which direction or qualities to keep and why, using the vocabulary. Revise ambiguous terms when feedback exposes a gap. Record accepted decisions and rejected directions with reasons and positive alternatives in `DESIGN.md`. A generated prototype or the agent's preferred option is not a user-approved winner.

Stop when the requested prototypes or implementation are delivered and the language reflects decisions actually made. If the user wants further iteration, use their feedback to define the next comparison rather than automatically generating more rounds. Publishing follows the user's separate authorization.
